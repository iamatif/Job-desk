# Scheduled job collection design
User-selected architecture: hosting cron runs Chromium with saved account keywords and persists verified Indeed/LinkedIn jobs; JSearch remains optional. Retain Node24, SQLite and the existing parser/worker. cPanel support is conditional on Node24, terminal/cron and executable Chromium with OS dependencies; a preflight must prove these before deployment.

Use an external CLI cron command, not browser sessions or an unauthenticated HTTP cron endpoint. Each account opts into a 6-hour default schedule, can choose 6/12/24 hours, posting range and optional backup. Cron reads saved workspace preferences at execution time, acquires a database lease against overlapping cron processes, runs serially headless, persists dated deduplicated job results and run history. Bound duration per account and total accounts per invocation. On CAPTCHA/access block record needs_attention and stop that browser. Optional explicit JSearch backup may then fetch; never bypass challenges. Dashboard reads durable results across restarts, separately from manually saved shortlist. Hosted origin must be explicitly configured, HTTPS cookies secure and existing local defaults preserved. No credentials or private data in deployment archive. No actual cloud activation until hosting compatibility and authenticated access available.

Alternatives: in-server timer is unreliable with Passenger idle shutdown; authenticated HTTP triggers require an always-running browser process and long HTTP timeouts. CLI cron fits the selected cPanel cron requirement and survives browser/dashboard closure.
